# 专业建设数据治理驾驶舱设计

日期：2026-07-27

## 1. 目标

在当前仓库根目录新增独立工程 `data-governance-dashboard/`，用一个可单独启动和构建的首页展示已沉淀的数据资产规模、已清洗或已匹配数量、覆盖率、待处理量、质量状态、来源和更新时间。

首期覆盖六类数据：

1. 产业链；
2. 产业环节；
3. 专业；
4. 国民经济行业；
5. 岗位；
6. 招聘信息。

看板采用“数据总量 + 已清洗量/覆盖率”双层口径。不同粒度的数据不能合并成一个总行数，首页只表述为“六类数据资产”，避免把产业链、专业、关系记录和招聘明细相加后形成没有业务意义的总数。

## 2. 使用场景

主要用户是项目负责人和数据治理人员。默认首页应在不操作筛选器的情况下回答以下问题：

- 当前已经治理了哪些数据；
- 每类数据有多少；
- 可比较的数据清洗到什么程度；
- 哪些数据仍需匹配、复核或继续跑批；
- 每个数字来自哪里、截至何时、采用什么统计口径。

页面同时支持日常推进和阶段汇报，但不设计成只适合投屏的纯成果大屏。

## 3. 非目标

- 不在首期建设后端服务或数据库。
- 不直接修改任何源 Excel、CSV、JSON、Parquet 或现有工程。
- 不在浏览器内解析大型数据文件。
- 不把 2014—2016 当前招聘跑批结果描述为 2014—2025 全量完成。
- 不把“57 个标准阶段环节”和“1,133 个精细产业节点”合并为同一种粒度。
- 不在首期加入账号、权限、在线编辑、人工审核或数据回写。

## 4. 技术方案

### 4.1 独立工程

工程目录为：

`/Users/liuhongzhe/Desktop/学堂/专业建设/Codex工程/data-governance-dashboard`

技术栈：

工程拥有独立的 `package.json`、`index.html`、源码、测试、数据刷新脚本和构建产物，不作为 `major-construction-platform` 的路由或子页面。

### 4.2 数据刷新方式

前端不直接读取源文件。`scripts/refresh-data.mjs` 通过 Node.js 执行。运行：

```bash
npm run refresh
```

时，由 Node 脚本读取源文件、校验结构、计算指标，并生成：

`src/data/dashboard-snapshot.json`

页面只读取这份有界静态快照。`npm run build` 将快照一起打入静态产物。

刷新脚本默认将工程父目录视为数据工作区，也支持显式传入：

```bash
npm run refresh -- --workspace-root /absolute/path/to/workspace
```

脚本不得依赖用户主目录、固定用户名或工程外的绝对路径。

### 4.3 原子快照

刷新脚本先在内存中生成候选快照并完成全部校验。只有校验通过后才覆盖 `dashboard-snapshot.json`。任何必需数据源缺失、字段不兼容或指标关系不成立时，命令返回非零退出码，并保留上一份有效快照。

快照中记录：

- 生成时间；
- 数据工作区；
- 每个数据源的相对路径；
- 源文件修改时间；
- 统计粒度；
- 指标定义；
- 数据质量状态；
- 已发现的警告；
- 当前招聘数据覆盖年份。

## 6. 快照数据模型

前端通过一个只读接口消费快照：

```ts
export interface DashboardSnapshot {
  schemaVersion: 1
  generatedAt: string
  workspaceRootLabel: string
  overallStatus: 'healthy' | 'partial' | 'stale' | 'error'
  assets: AssetMetric[]
  recruitmentPipeline: RecruitmentPipeline
  sources: SourceStatus[]
  warnings: string[]
}

export interface AssetMetric {
  id: 'chains' | 'stages' | 'majors' | 'industries' | 'positions' | 'recruitment'
  label: string
  primaryValue: number
  totalValue?: number
  coverageRate?: number
  status: 'validated' | 'partial' | 'review' | 'in_progress'
  definition: string
  grain: string
  sourceIds: string[]
  supportingMetrics: Array<{
    label: string
    value: number | string
  }>
}

export interface RecruitmentPipeline {
  inputRows: number
  validUniqueRows: number
  duplicateRows: number
  invalidRows: number
  formallyMatchedJobs: number
  mediumReviewJobs: number
  unmatchedRows: number
  formalRelationCount: number
  completedYears: number[]
}

export interface SourceStatus {
  id: string
  assetId: AssetMetric['id']
  relativePath: string
  selectedCandidate: boolean
  modifiedAt: string
  grain: string
  status: 'validated' | 'partial' | 'review' | 'in_progress' | 'missing'
  notes: string[]
}
```

`schemaVersion` 用于保护前端与刷新脚本的兼容性。前端遇到未知版本时显示清晰错误状态，不静默渲染。

## 8. 数据质量与异常处理

### 8.1 必需数据源

产业链、标准阶段环节、专业标准目录、专业匹配成果、行业标准目录、岗位匹配成果和招聘清单目录均为首期必需源。

必需源缺失时，刷新命令失败并列出缺失路径。旧快照不被覆盖。

### 8.2 结构变化

刷新脚本在读取前校验工作表和必需列。列缺失、工作表改名、JSON 缺少 `counts` 或数值不是非负整数时，刷新失败并指出源和字段。

### 8.3 一致性校验

至少执行以下约束：

- 产业链已标准化数不大于源产业链总数；
- 专业已确定关联数、待人工研判数和未匹配数均不大于专业总数；
- 岗位已匹配数 + 未匹配数 = 岗位总数；
- 招聘有效唯一数 + 重复数 + 无效数 = 输入记录数；
- 正式匹配招聘数、中置信待复核数和未匹配数之和不大于有效唯一记录数；
- 所有覆盖率在 0 到 1 之间；
- 招聘完成年份按升序且不重复。

不满足约束时不得发布新快照。

### 8.4 陈旧状态

前端根据快照生成时间和源文件状态展示状态。当前时间距离 `generatedAt` 超过 7 天时，前端将快照标记为“数据已过期”；任一源为部分完成或跑批进行中时，整体状态为“部分完成”。刷新失败本身由命令以非零退出码和错误清单报告，旧快照不被改写；页面继续展示旧快照，并按上述 7 天规则判断是否过期。

## 11. 验收标准

1. 工程可独立安装、刷新、测试、启动和构建。
2. 首页展示六类数据，不跨粒度计算虚假的总量。
3. 当前基线数字与源文件核对一致。
4. 招聘数据明确标记当前完成年份和跑批进行中状态。
5. 每个指标均可追溯到统计定义和相对来源路径。
6. 必需源缺失或结构变化时刷新失败，且旧快照不被覆盖。
7. 页面在桌面、平板和手机宽度下可读，无明显溢出或遮挡。
8. `npm run verify` 全部通过。
